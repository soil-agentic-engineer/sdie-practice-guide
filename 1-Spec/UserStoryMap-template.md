# 用户故事地图：<功能名>

> 方法论：User Story Mapping（Jeff Patton，权威推荐）。四层结构（Backbone / Details / Release slices / Out-of-scope）见 `SDIE-Spec-Guide.md` §4.2。
> RACI：PM/PO = A；Dev = R（协助梳理）；SME / Tech Lead = C。
> 每条 story 须 trace 至 PRD §4 的 Impact（IMP-x）；未挂 Impact 的 story 视为范围外候选（见 PRD §2）。
> 用法：复制本文件，把所有 `{{占位符}}` 替换为你的项目内容。横向是用户叙事流（按时间/步骤顺序），纵向是优先级（上方=必须有的最小骨架，下方=增强项），水平泳道切分发布（Release）。

**ID 方案（FEATURE 命名空间 + 层级路径前缀）**：活动 `ACT-{{FEATURE}}-{{序号}}`、任务 `TASK-{{FEATURE}}-{{活动序号}.{序号}}`、故事 `STORY-{{FEATURE}}-{{活动序号}.{主任务序号}.{序号}}`（如 `STORY-EXAMPLE-1.1.1`）。`{{FEATURE}}` 是产品/特性的稳定短标识。任务/故事 ID 前缀即编码父活动与主任务（层级可由 ID 推导，无需「所属活动」属性），唯有「跨任务关联」（一个故事服务多个任务步骤，多对多）由切片表列显式声明（见 §5、5.5）。

## 4. 细节（Details）：用户故事（Stories）与纵向优先级

> 故事卡片分「正面」与「背面」，不要在地图表面写长句：
> - **卡片正面（地图单元格内容）= 短标题/短语**，如「关键词搜索」「单规格加购」。地图靠短语快速浏览。
> - **卡片背面（详情，随卡片或工具记录）= 谁/要什么/为什么 + 验收标准**，可选使用助记模板。
>
> ⚠️ 关于「As a / I want / so that」：这是 Connextra（约 2001）提出、经 Mike Cohn《User Stories Applied》流行的**助记模板（mnemonic），不是敏捷/XP 的强制标准**。它最有价值却最常被省略的是 `so that`（价值）一句。把它当卡片背面"谁/要什么/为什么"的提醒即可，不要当成地图单元格必须填的格式。

**卡片背面详情模板（可选）**

```
角色（who）：{{角色}}
想要（what）：{{目标}}
以便（why / 价值）：{{价值}}        ← 最关键，常省略
主任务（可省略）：TASK-{{FEATURE}}-{{活动序号}.{序号}}
跨任务关联（其他支持的任务）：{{TASK-{{FEATURE}}-?}}   ← 可空；本故事逻辑上还服务哪些步骤（多对多）
验收标准（Acceptance Criteria）：
- 给定 {{前置条件}}，当 {{动作}}，则 {{预期结果}}
```

> 📌 故事 ID 为 `STORY-{{FEATURE}}-{{活动序号}.{主任务序号}.{序号}}`（如 `STORY-EXAMPLE-1.1.1`），其中 `{活动序号}.{主任务序号}` 对应主任务 `TASK-{{FEATURE}}-{{活动序号}.{主任务序号}}`（主任务由 ID 前缀编码，见 line 21；跨任务关联见 §5.5）。
> 每条 story 须过 INVEST 校验（Independent / Negotiable / Valuable / Estimable / Small / Testable，Bill Wake 2003），并 trace 至 PRD §4 的 Impact（IMP-x）。

| story（实现细节，卡片正面短语） | priority | backbone 挂接（activity/step） | impact（来自 PRD §4） | 主任务 |
|-------------------------------|----------|-------------------------------|------------------------|------------------------|
| <高优先故事> | P0 | 加购 / 点击加购 | IMP-1（买家即时下单） | TASK-{{FEATURE}}-2.1 |
| <低优先故事> | P2 | 结算 / 确认订单 | IMP-2（客服免转人工） | TASK-{{FEATURE}}-3.1 |
